# 地形変形・道路建設ゲーム 技術プロトタイプ

SDF ボクセル地形を自由に変形し、道路を通し、トンネルを掘る。地質に応じて崩落する。
TypeScript + Three.js (WebGL2) + Web Worker、依存は three だけ。

## 結論: TypeScript + Three.js で実現可能

以下はすべて **このリポジトリでの実測値** (`npm run bench`, Node 22, 4 コア)。

### 新しいチャンクを 1 つ作る (Worker、チャンクごとに一度だけ)

| 処理 | 実測 |
|---|---|
| 手続き密度生成 `fillChunkField` | 13.1 ms |
| 等値面抽出 `surfaceNets` (約 2900 三角形) | 1.6 ms |
| **合計** | **14.7 ms** → Worker 1 本あたり 68 チャンク/秒 |

### 編集する (対話的な操作、こちらが体感を決める)

| 処理 | 実測 |
|---|---|
| CSG 球ブラシ r=2.5 m | **0.07 ms** |
| フィールドのコピー (Worker 転送用) | 0.008 ms |
| 再メッシュ | 1.6 ms |
| **チャンクあたり合計** | **1.7 ms** (8 チャンクに波及しても 13.6 ms) |

ブラシが実質タダなのは、**チャンクの密度フィールドをキャッシュしている**ため。
編集で手続き生成をやり直さない。コストは再メッシュに集中する。

| ブラシ種 | 実測 |
|---|---|
| 球 r=6 m | 0.39 ms |
| トンネル掘進 r=3 m × 16 m | 0.28 ms |
| 道路コリドー 幅 8 m | 1.44 ms |
| 崩落コーン | 0.29 ms |
| 沈下ボウル | 1.18 ms |

### 崩落の質量保存 (膨れと自己閉塞)

破砕された岩は元の岩よりかさばる。だから現実の崩落は**自分の瓦礫で詰まって止まる**。

| 材料 | 膨れ B | 6 m 断面が閉塞するまでの高さ `Ht/(B-1)` |
|---|---|---|
| 砂・表土 | 1.15 | 40.0 m |
| 粘土 | 1.25 | 24.0 m |
| 砂岩 | 1.40 | 15.0 m |
| 花崗岩 | 1.50 | 12.0 m |

崩落高は `min(アーチ形成高, 閉塞高, 土被り)`。土被りが先に尽きれば地表に貫通して**陥没**になり、
陥没の深さは体積の不足分から決める。膨れの小さい土砂が遠くまでチムニーするのは、
浅い坑道の上に陥没が生じる実際の理由そのもの。

### 地盤の評価 (解析式のみ。応力場は一切解かない)

| 処理 | 実測 |
|---|---|
| Terzaghi 支持力 1 点 | 0.2 µs |
| 基礎 1000 本を 1 ティックで | **0.26 ms** |
| 支持力ヒートマップ 4068 点 (ブラウザ、レイキャスト込み) | 72 ms |

### ブラウザでの実測 (4 コア + SwiftShader ソフトウェア GL)

565 チャンク完全常駐 / 324,380 三角形 / エラーゼロ。`npm run smoke` 参照。

Worker のバックログを浅くすると**チャンク生成速度がフレームレートに縛られる**。
10 fps で 3 Worker の場合、キューは 40 ms で枯れて残り 60 ms は全 Worker が遊ぶ。
バックログを深くして 14.1 s → **4.9 s** (2.9 倍)。

## 元案から変更した 3 点

### 1. 「既存の GPU 経路」はブラウザに存在しない

WebGL2 に compute shader は無いため、GPU メッシュ化には `three.webgpu.js` の
WebGPURenderer + TSL compute が必要になる。だが上の実測どおり CPU で足りるので、
**WebGL2 + Web Worker プールでの CPU Surface Nets** を採用した。WebGPU は不採用。

`SharedArrayBuffer` も使っていない。`ArrayBuffer` の transfer で十分速く、
COOP/COEP ヘッダ設定が不要になるのでデプロイが楽。

### 2. 決定論の罠 (最大の落とし穴)

案は「ディスクには何も置かない、差分ブラシだけ保存」。これはロード時にベース地形が
**ビット単位で再現される**ことが前提。しかし ECMAScript は `Math.sin/cos/pow/exp` の
精度を実装依存としており、エンジン/CPU 間で一致する保証がない。あるブラウザで保存した
セーブが別のブラウザでは別の地形になり、差分ブラシが全部ずれる。

→ 密度関数は**整数ハッシュベースの value noise のみ**で構成し、超越関数を一切使わない。
`Math.sqrt`/`floor`/`abs`/`min`/`max` は IEEE-754 で厳密に規定されているので使用可。
`tests/determinism.test.ts` が `src/core/hash.ts` / `density.ts` / `geology.ts` を
grep して禁止関数の混入を機械的に防いでいる。

### 3. 断面ビューで地質関数を GLSL に二重実装しない

平面クリップ + キャップ描画にすると地質関数を GLSL 側にも書き、TypeScript 側と永久に
同期させる必要が出る。代わりに **切断面を CPU で 256×192 サンプルして `DataTexture` に
焼き、平面クアッドに貼る**。地層関数の実装は TypeScript の 1 つだけで済む。
断面を動かした時のみ再生成。

### ハイブリッド 3 層

1. **ベース** — 手続き密度関数。ディスクには何も置かない。
2. **差分** — チャンクごとの CSG ブラシ列。**これが唯一の保存対象**。
3. **ベイク** — ブラシ数が 32 を超えたらフィールドに畳んで列を破棄。
   以降そのチャンクはボクセルを保存する (Int16 量子化、±8 m クランプ、0.24 mm 刻み)。

セーブサイズはベイクの有無で桁が変わる。編集が軽いうちは**ブラシ列だけ**なので
数 KB (未編集なら 100 バイト未満)。崩落を起こしてチャンクがベイクされると
1 チャンクあたり約 157 KB のボクセルを持つので、実測で 9.4 KB → 1.1 MB (7 チャンクベイク) になる。
これはリロード時のブラシ再生コストを有界にするための意図的な交換。

沈下も崩落も陥没もすべて CSG ブラシとして書き戻すので、**保存経路は 1 本のまま**。
新しい「壊れた地形」表現は要らない。

### チャンクの継ぎ目

各チャンクは `[CELL_LO, CELL_HI]` のセルを所有し、+x/+y/+z 側の面を跨ぐ四角形は
隣のチャンクが出す。両者は同一の決定論的密度関数を同一の world 座標で評価するので、
**チャンク間で一切通信せずに面が閉じる**。

`tests/surfaceNets.test.ts` が 2×2×2 ブロックを 0.1 mm 精度で溶接し、内部に穴 (1 三角形の辺)
と非多様体辺 (3 枚以上) が 0 であることを検証。さらに「符号が変わる格子辺がちょうど 1 つの
チャンクからのみ出力される」ことを直接確認している。

> チャンク座標は float32 のチャンクローカルなので、共有頂点は**ビット一致ではなく**
> 1 µm 程度の一致。原点近傍で精度を保つための意図的な設計で、視覚的な影響はない。

### トンネル支保工 (中核メカニクス)

岩盤分類から 2 つの数字を出し、そのままゲーム性にする。

- **無支保スパン** = `(0.7 + 0.0021·RMR²) / (1 + σv/4500)` — Bieniawski のチャートの形に合わせた
- **自立時間** = 超過率の 1.5 乗で減衰。無支保スパン以内なら ∞

掘削幅が許容スパンを超えると劣化タイマーが動き、
`ひび割れ → 内空変位 → 崩落間近 → 崩落` と段階的に進む。時間内に支保工
(吹付け ×1.6 / ロックボルト ×2.3 / 覆工 ×6) を入れれば恒久的に安全。
土被りが薄い区間では崩落が地表に抜けて**陥没**になる。

| 深さ | 局所 RMR | 土被り | σv | 無支保スパン | 6 m 断面に必要な支保 |
|---|---|---|---|---|---|
| 5 m | 7 (表土) | 3 m | 42 kPa | 0.8 m | 不可能 |
| 10 m | 11 (砂) | 8 m | 130 kPa | 0.9 m | 不可能 |
| 16 m | 12 (粘土) | 14 m | 240 kPa | 1.0 m | 不可能 |
| 22 m | 17 (粘土) | 19 m | 320 kPa | 1.2 m | 覆工 |
| 30 m | 55 (砂岩) | 25 m | 467 kPa | 6.4 m | 不要 |

RMR は**開口部の周囲の岩**から取る (土被り全体の最弱材料ではない)。
このマップは全カラムが表土で覆われているので、後者にすると全深度で RMR≈7 になり、
どんな支保工でも支えられなくなる。詳細は `sim/stress.ts` の `rockQualityAround`。

### 「掘削」と「トンネル掘進」の違い

**物理は同じ。** 押したボタンで岩の挙動が変わることはない。違いは 2 つだけ:

| | 掘削 | トンネル掘進 |
|---|---|---|
| 形状 | 球 | 2 点間の掃引カプセル |
| 単位 | 単一の空洞 | 支保単位の連続断面 (地質が変わる場所ごとに別評価) |

どちらも**天端のある掘削は「空洞」として登録**され、無支保スパン・自立時間・支保工の
同じ規則で判定される。天端の無い掘削 (地表の切土・盛土) は登録されず、崩落もしない。

これは以前の実装の不整合を直したもの。以前は掘削に安定性判定が一切無く、
地下に任意の大きさの空洞を掘っても何も起きなかった。

### 同一の物理: `sim/rockmass.ts`

「支えの無い岩がどれだけ張り出せるか」は 1 か所にしか書かれていない。
トンネルの天端、自由掘削の地下空洞、片持ちのオーバーハングは同じ物理的な問いなので、
`unsupportedSpan(RMR, σv)` を全員が使う (片持ちは両端支持の約半分なので ×0.5)。

`shallowCoverFactor` で薄い天端は連続的に弱くなる。
1 m の砂岩は 6 m スパンに対してはアーチではなく単なる板なので、良質な岩でも支えられない。
閾値ではなく連続関数にしているのは、任意の深さの前後で同じ地盤が全く違う挙動をしないため。

**天端が無ければトンネルではない。** 地表に沿って掘進すると天端は空中にあり土被りは 0 m
なので、`open_cut`（開削）として崩落の対象外になる。開削で物理的に自然な破壊は法面の
スランプだが、斜面崩壊は未実装なので溝は開いたまま残る (意図的)。

### 支持を失った岩は落ちる (`sim/detach.ts`)

再メッシュと同じフィールドを 1 回走査して 2 つを同時に求める。**編集されたチャンクのみ**が
対象で、手続き地形には分離岩塊が 1 つも無いことを実測済み (48 チャンク走査、0 個)。

1. **分離** — 固体ボクセルの 6 連結成分。走査ボックスの面に触れる成分は
   「外に続いている可能性がある = 支持されている」とみなす。**保守的なので正当な地形を
   誤って消さない。**
2. **オーバーハング** — 直下が空のボクセルについて、支持された柱までの水平距離を
   2D 距離変換で求め、`0.5 × unsupportedSpan` と比較する。

落下は既存の CSG 経路に乗る: 岩塊を除去 → 破片をスポーン → 膨れた体積の瓦礫を着地点に堆積。
支保済みの断面の近傍は除外する (支保したのに天端が落ちたら支保が効いていないのと同じに見える)。

大きな崩落は 1 フレームで消えるのではなく**数ラウンドかけて崩れて収束する**
(20×20 m のアンダーカットで 10〜11 ラウンド、3,400 m³、体積は単調減少)。

**既知の限界**: Worker は 1 チャンク分のフィールド (34³) しか見えないので、
**チャンクをまたぐ大きな島は検出されない**。安全側の失敗。将来 3×3×3 集約パスに上げられる。

### 可読性 (理由が見えない崩壊はバグと区別がつかない)

- **断面ビュー** (`C`) — 地層・空洞・破片を横から見る
- **支持力余裕度ヒートマップ** (`H`) — **基礎の根入れ深さ**の材料で評価する。
  地表の材料で評価すると全面が表土になり一色になってしまう
- **段階的予兆** — 数十秒かけて進行。圧密沈下は実際に時間がかかるので物理的にも正しい
- **数値の露出** — 「許容支持力 200 kN/m² / 作用 340 kN/m²」「RMR 45、無支保スパン 3.2 m、残り 18 s」
- **崩落土 (`Mat.RUBBLE`)** — 盛土と別材料にした。許容支持力 152 kN/m² でマップ中最弱なので、
  崩落跡はヒートマップで赤く出て、そこに基礎を置けないことが見える

## 使い方

```bash
npm install
npm run dev      # http://localhost:5173
npm test         # tsc --noEmit && node --test (69 テスト)
npm run bench    # 上記の実測値を再測定
npm run build    # 型チェック + 本番ビルド
npm run smoke    # ヘッドレス Chromium で E2E (スクリーンショットを test-results/ に出力)
```

操作:

- 左ドラッグ: 視点回転 / 右・中ドラッグ: 平行移動 / ホイール: ズーム
- `1`〜`6`: 掘削 / 盛土 / 道路 / トンネル掘進 / 支保工設置 / 地質調査
- 道路とトンネルは 2 回クリック (始点 → 終点)
- `C`: 断面ビュー / `H`: 支持力ヒートマップ

トンネル崩落を見るには: `4` でトンネル径を 9 m 程度にし、浅い斜面に掘進 → 支保工を入れずに待つ。

## テスト

`npm test` — 69 テスト。特に守っているのは:

- **決定論** — ハッシュのゴールデン値固定 + 禁止 Math 関数の grep 検査
- **継ぎ目** — 2×2×2 ブロックが 0.1 mm 溶接で水密。格子辺の所有権が重複も欠落もない
- **ブラシ** — SDF の符号と AABB の健全性、適用順序、差分リプレイの一致
- **セーブ/ロード** — 全チャンクのフィールドとマテリアルが完全一致。
  シード不一致とバージョン不一致は拒否。ベイク済みチャンクは等値面付近が 1 mm 未満の誤差
- **トンネル** — 過大スパンは予兆を経て崩落し CSG ブラシを出す。
  支保後は崩落しない。掘削時点で状態が確定する (最初のティックまで "安定" と誤表示しない)
- **質量保存** — 瓦礫の体積 = 除去体積 × 膨れ。残存空洞は落ちた岩より小さい。
  崩落後に坑道が崩落土で埋まっている
- **開削** — 地表に沿った掘進は `open_cut` になり、自立時間は Infinity、
  200 ティック回しても崩落ブラシを 1 つも出さない。覆工を入れても「支保済」にはならない
- **土被りの連続性** — `shallowCoverFactor` は単調で、深いほど広いスパンを許す
- **掘削の統一** — 地下の掘削は空洞として登録され支保なしで崩落する。
  地表の掘削は登録されない。同じ場所を繰り返し掘っても空洞は 1 つ
- **分離とオーバーハング** — 浮いた岩塊は 1 回だけ報告される。
  ボックス面に触れる岩塊は「支持されている」とみなされ消されない。接地した柱は無傷。
  **手続き地形 48 チャンクで検出 0 件**(誤検出しない側の確認)。
  弱い岩は短い張り出しで壊れる。支保済み断面は除外される。カスケードは収束する

`npm run smoke` — 実ブラウザで 29 チェック。WebGL2、Worker プール、
掘削 → 崩落 → 埋没の確認 → 開削が崩れないこと → アンダーカットした岩の落下 → セーブまで通す。

## スコープ外 (拡張点だけ用意済み)

- **斜面崩壊 / 法面スランプ** — 未実装。開削断面の法面は立ったまま残る。
  開削で物理的に自然な破壊はこれなので、入れるなら次の優先度
- **不同沈下 + 構造物 FEM** — `settlementBowl` ブラシと `bearing.ts` の `settlementRate` は実装済み。
  行列フリー共役勾配のトラス解析は 1812 自由度で 19 ms 実測なので、0.5 s ティックに十分乗る
- **地下水** — 透水性フィールドは物性テーブルに用意済み、未使用
- **チャンクをまたぐ分離判定** — 3×3×3 を集約する走査パスに上げれば対応できる
